# 同步上游的做法評估（2026-11-23）

## 1. 問題

`refactor` 從 v2.3.2 起逐版同步上游（3.21）。為了讓同步可行，訂了兩條原則：

- **3.4 第 3 點、3.19**：上游常改的程式不搬、不拆。`pipeline.py` 只拆出 v1.6 以來沒改過的音高後處理和歌詞文字；`Jobs`、`process_song`、`separate_uvr` 等上游常改的定義都留在原處。
- **`next-version-plan.md` 第 1 節**：每在上游的檔案改一處，同步時就多一處要手動合併，所以修上游的 bug 也盡量少碰上游的檔案。

結果是很多事做不下去，或做得很彆扭：`pipeline.py` 拆不開（4600 多行）、`Jobs` 搬不出來、修 bug 要先算同步成本。2.3.5 又出現同一個功能兩邊各做一次的情形（第 5 批的第一段分離退回和上游 `6ee0964`）。

根本原因是**同步的單位是檔案和行號**。fork 一搬動、一改寫，patch 就套不上。

## 2. 目前的同步工具

`tests/tools/upstream_map.py`（3.21）：找出每個 hunk 落在上游哪個最上層定義裡，再找那個名稱現在在哪個檔案，把 patch 的路徑改寫過去，用 `git apply --reject --recount` 套。

限制：

- **fork 改過的定義，patch 套不上**（`.rej`），要手動合併。fork 改得越多，每次同步的手動量越大，這就是第 1 節兩條原則的由來。
- **patch 對換行敏感**：2.3.5 的 `upgrade_separation` 內容和上游完全相同，但工作目錄是 CRLF，patch 是 LF，就被拒絕了。
- **上游新增的定義**（例如 2.3.5 的 `submit_unfinished`）、**模組層級的 import、常數**，要依報告手動放。
- 只能找原本拆出去的範圍（app.py → `app.py`、`leihu/web/`；pipeline.py → `pipeline.py`、`leihu/pitch.py`、`leihu/lyrics_text.py`）。

## 3. 可以考慮的方向

| 方向 | 做法 | 好處 | 代價 |
|---|---|---|---|
| **A. 以定義為單位的三方合併** | 對上游每個改過的最上層定義，用「舊上游版／新上游版／fork 目前版」三份做三方合併（`git merge-file`），fork 的定義在哪個檔案都可以 | fork 可以自由拆檔、改函式內容；只有兩邊改到同一段才需要手動 | 要寫工具並驗證；改名、合併、拆開定義時要登記名稱對照 |
| B. 上游優先 | 真的是 bug 的修正回報給上游 | 分歧越來越小 | 看上游接不接受；不是每個修正都適合送上游 |
| C. 把上游當規格重新實作 | 看上游每個版本的改動，在 fork 的結構裡重寫，用契約、數值基準確認行為一致 | 結構完全自由 | 每個版本都要人力；舊分支 `sync/upstream-2.3.2` 就是這樣做，很耗時 |
| D. 覆蓋層 | 上游檔案保持原樣，fork 的修改放在另一個模組、啟動時替換上游的函式 | 同步完全不衝突 | 函式內部的修改等於整個函式重寫；上游改了被替換的函式時，fork 不會發現，靜默失效 |
| E. 完全分家 | 不再定期同步，只挑上游有價值的功能手動搬 | 最自由、最省同步成本 | 上游的修正要自己追 |

## 4. 方向 A 的原型：`tests/tools/defmerge.py`

```
python tests/tools/defmerge.py <舊上游> <新上游> <fork 的參照> --out=<資料夾> [--expect=<參照>] [--all]
python tests/tools/defmerge.py <舊上游> <新上游> --tree=<資料夾> --out=<資料夾>
```

做法：

1. 解析舊、新上游的 `app.py`、`pipeline.py`，列出每個最上層定義（函式、類別、模組層級的指定）。
2. 在 fork 裡依名稱找這個定義：app.py 的在 `app.py`、`leihu/web/*.py`，pipeline.py 的在 `pipeline.py`、`leihu/*.py`、`leihu/core/*.py`（`GROUPS`，可以擴充）。名稱改了的登記在 `RENAMES`。
3. 上游改過的定義：
   - fork 的版本和舊上游逐行相同（只去掉頭尾空行，行尾空白、**註解都要算**，見第 12 點）→ 直接換成新上游的。
   - 不同 → `git merge-file` 三方合併；兩邊改到同一段（或相鄰的行，和 git 合併相同）就留下衝突標記，列為「衝突」。
   - app.py 的定義先把 `@app.X` 換成 fork 的 `@bp.X`（和 `upstream_map` 相同的規則）。
4. **版號**（`VERSIONED`：`VERSION`、`USER_AGENT`；`VERSION` 檔）：三方合併前先把三份裡的版號（含 fork 的第 4 段）換成記號，合併後一律換成 3.15 的「新上游版本＋.1」。版號本身不會再衝突，fork 在同一行的註解、F1 改過的網址照樣留著。
5. 上游新增的定義：`PLACE` 有登記（名稱或 `re:` 模式）就放那個檔案（有鄰居在那裡就接在後面，沒有就放最後）；沒登記就放在上游順序中前一個鄰居現在所在的檔案、接在它後面。放到別的檔案時，用到它、又沒有 import 的檔案列為「手動」（只列出來：import 要和那個檔案原本的寫法排在一起）。
6. 上游刪掉的定義：fork 沒改過才刪，改過就列為「手動」。
7. 模組層級的 import：上游新增的，`IMPORT_TARGET` 有登記的組（目前只有 pipeline.py）已經有就略過、沒有就加在最後一個 import 後面；app.py 拆成很多檔案，列為「手動」。其他模組層級的敘述（`if` 區塊、運算式）只列出來。
8. `--all`：app.py、pipeline.py 以外上游改過的檔案（`gpu_worker.py`、`static/*`、`installer/*` 等）整個檔案三方合併；fork 沒改過就直接換。
9. 寫出合併後的檔案到 `--out`（不動工作目錄，`--tree` 時保留原本的 CRLF／LF）；`--expect` 依名稱和指定的參照比較，分「內容不同」「位置不同」。
10. 不自動處理、列為「手動」的：同一個敘述指定好幾個名稱（`A = B = 1`）、同一個檔案有兩個以上同名定義、解包指定與 `X[...] =` 這類指定（歸在模組層級敘述）、上游刪掉的模組層級敘述與 import、用到它的定義搬到別的檔案的新 import、`__future__`、在 import 位置之前就用到的新 import、替換範圍互相重疊的檔案。
11. 套用編輯：同一個位置的插入照上游順序合成一塊；同一個起點先替換、再插入；替換範圍重疊的整個檔案不寫出。
12. 比對「有沒有改過」只去掉頭尾空行，行尾空白、註解都算（三引號字串裡的行尾空白是資料）；Blueprint 改寫只改裝飾器那一行；整個檔案合併保留檔尾空行；git 參照打錯直接中止，不當成檔案不存在。
13. 單元測試：`tests/test_defmerge.py`（52 個測試函式，含參數化共 64 項；舊上游、新上游、fork 都用暫存資料夾，讀二進位檔那一項用這個 repo 的 `HEAD`）。
14. 不能自動處理的也列為「手動」、不寫出（PR #26 審查）：從 git 參照讀到二進位檔；fork、舊上游、新上游有一份找不到該有的版號；`git merge-file` 執行失敗（不是有衝突）；星號 import；新增的 import 和目標檔案裡同名的 import 或定義衝突。衝突標記固定用 merge 樣式（不受使用者的 `merge.conflictStyle` 影響）；`app.static_folder`、`app.response_class` 和 `upstream_map` 一樣換成 `current_app.*`；命令列用 argparse，拼錯的選項回報錯誤。

### 5.1 重跑過去三次同步

fork 用每次同步前的 commit，`--expect` 用手動同步後的 commit：

第一版原型（2026-11-23）：

| 2.3.3 | `15eaf90^` → `69659e9` | 23 | 9 | 0 | 4 | 10 | 版號 2（`VERSION`、`USER_AGENT`）、真正衝突 2（`take_export`、`main`）、fork 的調整 1（`QUEUE_FILE` 改放 `P.DATA`）；位置不同 6 |
| 2.3.4 | `abc73fb^` → `8b6e168` | 6 | 0 | 0 | 2 | 4 | 版號 2、fork 的調整 1（`UI_PREFS` 改放 `P.DATA`） |
| 2.3.5 | `263833a` → `43ddbb0` | 16 | 8 | 0 | 2 | 6 | 版號 2；位置不同 1（`submit_unfinished`） |

| 版本 | 直接換 | 版號 | 衝突 | 新增 | 手動 | 和手動同步不同 |
|---|---|---|---|---|---|---|
| 2.3.3 | 9 | 2 | 2（`take_export`、`main`） | 10 | 3（`background.py` 用到 `QUEUE_FILE`、`app.py` 用到 `queue_saver`、`restore_queue` 要 import；後兩項是 PR #26 審查修正後才列出來的） | 衝突 2、fork 的調整 1（`QUEUE_FILE`） |

- 這三次同步裡，所有「內容不同」都是工具標了衝突的（`take_export`、`main`），或是 fork 在同步時另外做的調整（`QUEUE_FILE`、`UI_PREFS` 放 `P.DATA`，工具本來就不會知道）。**這只代表這三次沒有看到靜默錯誤**：`--expect` 只比定義的內容和所在檔案，不比定義之間的順序和模組層級敘述。

- 2.3.5 加 `--all`：`gpu_worker.py`、`static/app.js` 三方合併成功、和手動同步相同；`VERSION` 檔照版號規則；`installer/leihu.nsi`（2 處）、`static/help.html`（4 處）、`static/index.html`（1 處）衝突，都是版號和更新說明，和手動同步時一樣要手動改（這些檔案沒有套版號規則：說明頁裡的舊版號是更新紀錄，不能換）。

`tests/private/defmerge/make_split.py` 把 `263833a` 的 20 個上游常改的定義（`Jobs`、`separate_uvr`、`step_separate`、`vocal_model`、`karaoke_model`、`process_song`、`fine_job`、`youtube_job`、`step_youtube` 等）搬到 `leihu/core/{jobs,separation,process,youtube}.py`，再同步 2.3.5：`vocal_model`、`karaoke_model`、`separate_uvr` 在 `leihu/core/separation.py` 裡照樣合併，內容和手動同步相同；不同的只有版號，以及這三個定義的位置（本來就搬走了）。

### 5.3 壓力測試：fork 大改過的定義

在第 5 批（`bd140a0`，改了 `separate_uvr`、`vocal_model`、`karaoke_model`）上同步 2.3.5：這三個都正確標成衝突，衝突區只有兩邊改到的那幾行（例如 `vocal_model` 只有 `if` 那一行：fork 改成 `_uses_hq`、上游加了 `_HQ_FAIL` 的條件），其他 5 個定義照常直接換。

### 5.4 合成測試：兩邊改到同一個定義的不同地方

過去三次同步都沒有出現「兩邊都改了同一個定義、但改的地方不重疊」的情形（上表的「三方合併」都是 0），所以另外做了合成測試（`tests/private/defmerge/synthetic.py`）：在拆檔後的副本裡，fork 在 `voice_fit` 開頭加一行程式、在 `clean_lrc` 只加一行註解，上游 2.3.5 改的是這兩個函式的其他地方。兩個都三方合併成功：fork 的修改留著，上游的改動也都拿到，沒有衝突標記。

原型第一版用「去掉註解和空白」判斷 fork 有沒有改過，fork 只加註解時會被當成沒改過、直接被上游蓋掉；改成逐行比對後才通過這個測試。

## 6. 結論與建議

**建議採用 A，搭配 B。**

- A 把同步的手動量從「fork 改過的每個定義」降到「兩邊改到同一段的地方」。過去三次同步，除了版號，只有 2 個定義真的要手動合併（都在 2.3.3）。
- 有了 A，第 1 節的兩條原則可以放寬：
  - `pipeline.py` 可以依功能拆開，條件是**名稱不變**（`pipeline` 仍然轉出同一個名稱，測試和沙盒的 `P.<名稱>` 替換才不會失效，3.19 的考量照舊），或在 `RENAMES` 登記。
  - 修上游的 bug 不用再迴避上游的檔案；只要上游之後沒有改到同一段，同步時就自動保留。
- B 適合真的是上游 bug、改動又小的修正（例如 `import subprocess`、`_set_priority`、M6）：上游修了，同步時就是「直接換」，fork 少一處分歧。

採用時要注意：

- **不要為了排版改動上游的定義**：整段縮排、重新排版會讓 `git merge-file` 把整段當成改過（2.3.3 的 `main` 就是這樣）。fork 要包一層條件時，優先抽成新的函式呼叫，不要把上游的整段縮排進去。
- **版號這類每次都會衝突的常數**，在工具裡固定用 fork 的規則處理（3.15：上游版本＋.1），不要每次手動（已做，第 4 節第 4 點）。
- **放置位置要能指定**：新增定義的預設規則（前一個鄰居）大多對，但啟動時的背景工作、共用的輔助函式要依用途放。用「名稱或模式 → 檔案」的對照（`PLACE`，已做）；新的放置決定要補進 `PLACE`。

## 8. 沒有驗證的部分

- 過去的同步沒有真實的「兩邊改同一個定義的不同地方」案例，只有合成測試（2 個定義）和單元測試。
- 以定義為單位只處理 `app.py`、`pipeline.py`（其他檔案用 `--all` 整個檔案三方合併）；類別是整個當成一個定義合併（`Jobs` 裡任何一處被上游改到，就是整個類別做三方合併），沒有拆到方法層級。
- 拆檔的壓力測試只搬文字，沒有確認搬完的程式能不能執行、`pipeline` 的轉出是否齊全。
- 沒有測巢狀定義改名、同名定義（例如 app.py 的路由 `furigana` 和 `pipeline.furigana`）的處理；同一組裡有兩個同名定義時列為「手動」（有單元測試）。
- 跨檔案的 import 檢查只看名稱有沒有出現（排除 `P.名稱`），字串或註解裡出現同名的字也會列出來；只列出、不自動加。
